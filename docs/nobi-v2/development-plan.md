# 开发计划与阶段门槛

本轮只完成 Phase 0。以下是下一阶段及后续工作的依赖计划，不构成已开始实现或生产发布。时间按约单人有效工作日估算，取得设计稿/环境后重新评估，不以期限跳过资源或安全验收。

## Phase 0：完整审计与基线（本轮）

产出：完整审计、逐文件资源哈希/渲染区域清单、Supabase 契约/风险、统一架构、开发计划、验收表、实际测试结果。提交仅含 docs，父提交为 a0bb939 完整 SHA，main 保持原值。

已有测试执行尝试和命令结果已记录；原生测试引导失败、生产权限未知、真实视觉/E2E 未执行均明示。阶段文档可交付，基线不能宣称无缺陷或可发布。

## Phase 1：工程与回归基础（建议 3–5 日）

目标：在不更改原游戏规则/视觉的条件下，得到可重复构建、可检测资源破坏、可使用隔离后端的三端基础。

顺序及交付：

1. 建立 PNG 来源/产物哈希守卫与围棋渲染守卫；补固定视口/DPR 的棋盘、手牌浏览器截图。确认 V2.1 正式稿文件映射。
2. 记录现有游戏可玩路径和已知故障；补真实规则/状态回归，而不是复刻实现或仅验证按钮存在。将本轮探针复现转换为独立缺陷用例。
3. 建立单一源码和白名单构建，Web/mobile 产物分开；原始 PNG 逐字节复制；Capacitor 指向生成产物。公共壳构建引入锁定的 Vite/TS，遗留 script 保持原样。
4. 统一配置就绪/认证用户接口，pin Supabase SDK；开发默认使用隔离实例/本地 mock，不把生产作为开发数据源。
5. 建立产物敏感文件检查；提出依赖/签名材料治理变更，确认暴露及轮换需求，不擅自改历史或生产密钥。
6. 配齐 Android SDK/Gradle/cache/生成目录；准备 macOS iOS 工具链，修正模板测试与真实业务覆盖。
7. 从已有脱敏导出/隔离环境建立 Supabase 契约基线；恢复同一自建技术栈。未取得快照时可继续资源/构建工作，数据实现保持待验证。

门槛：资源 56/56、受保护围棋视觉一致、Web/mobile 引用全可解析、配置缺失/错误/正常三类行为可复现、不会写生产、至少一套真实浏览器业务回归、测试环境契约可复核。需要声明未齐全的设备能力，不能以 echo build 通过代替。

回退：工程提交与游戏缺陷修复分开；出现新行为回归时退回原 adapter/入口。旧休闲玩法及基线资源保留为对照，不直接覆盖两套引擎。

## Phase 2：新大厅、平台能力、音乐（建议 4–7 日）

- 建立深蓝电竞壳、GameRegistry、加载/离线/错误状态、导航和游戏适配生命周期。
- PC 保留三游戏；mobile 构建排除 CS code/下载脚本，运行注册表和深链双重校验。
- 移动按已有 V2.1 正式稿实现，不另作视觉设计；支持安全区、横竖屏、Android 返回、iOS 中断。
- 加入 AudioService、master/bgm/sfx、静音、偏好恢复、后台暂停与有授权的曲目。
- 旧游戏通过独立同源子页面接入，验证 Canvas/DPR/手牌操作和事件/频道销毁；不移除原牌面或换棋盘。
- 排行榜/个人名次先做明确标注的测试数据状态，不能发布为真实竞技排名。

门槛：大厅扩展不改硬编码分支、连续切换无资源泄漏、移动无 CS 入口/资源、音频手势/设置/生命周期真机通过、正式稿逐页对齐、旧游戏回归通过。

## 独立缺陷流：旧游戏稳定性（建议 4–8 日，随证据调整）

与大厅提交分开处理本轮 R05/R08/R19 等问题：围棋重开计数/劫点、重复消息、AI 试落子；掼蛋网络处理器、统一牌对象/实际手牌接入、多人 DOM/计时器生命周期。明确保留现有规则/视觉的边界，每个修复有失败用例与通过证据。

这条工作流可能先于 Phase 2 接入真人联机完成；不以大厅“已接入”代替修复。规则改动另登记需求和规则版本，不顺带全面重写进贡/计分。

## Phase 3：可信战绩、排行榜与个人排名（建议 6–10 日）

前置：真实 schema 契约、可信 Auth UID、可稳定的多人通路和隐藏手牌。制定每游戏计分、赛季、认输/掉线、AI 排除、同分名次规则。

- 在同一自建 Supabase 的隔离测试环境新增 nobi_v2 数据、受限 RPC、幂等积分流水。
- 建立可信结果验证；匿名、观战者、伪造结果、重放、抢位、全员手牌可见等测试必须失败。
- 事务结算与个人名次/榜单使用同一数据源；服务端重试不重复入分，分页不漏不重。
- 不导入未知历史战绩，不使用用户自选 rank 当积分，不新增 MongoDB。
- CS 结果暂无可信服务器战报时保持非计分状态，PC 启动功能仍保留。
- 迁移/回滚脚本先通过 staging；本阶段计划不授权执行生产变更。

门槛：双人围棋/四人掼蛋对局与结算真实验证、RLS/grants/RPC 负向测试通过、同分/无排名/分页/重复/并发/断线均符合规则，旧休闲模式仍可运行。

## Phase 4：三端全面验收与发布准备（建议 3–5 日）

执行[验收矩阵](acceptance.md)，生成受保护资源校验、真机/浏览器、可信结果与权限、签名包扫描报告；复核当时 Android/iOS 发布要求。准备备份、灰度/回滚与版本说明。

发布准备交付可审查的产物与迁移方案；实际生产 SQL、部署、main 合并、正式签名分发需后续明确授权。本轮不启动这些动作。
